# Deploying Counterbill on Render Free with Neon Free PostgreSQL

Status on 31 October 2026: **prepared and exercised locally; not yet deployed.** The hosted investigation, survey revision, export and restart recovery have not been run on a hosted URL, and nothing here says they have. Section 4 is the checklist that decides that, and section 5 lists what was measured locally.

Nothing in this setup uses a paid service. If Render or Neon asks for a card or offers an upgrade at any step, stop and do not continue.

## 1. What runs where

| Piece | Where | Notes |
|---|---|---|
| Web app + investigation worker | **One** Render Web Service (Docker, plan **Free**) | `render.yaml`. The container runs `scripts/start-render.mjs`: migrations first, then `next start` on Render's `PORT` (bound to `0.0.0.0`) and the worker supervisor. No paid Background Worker. |
| PostgreSQL | Neon Free project | Cases, documents (as `bytea`), exports, events, the work queue and rate limits all live here. The container's disk is not used for anything that must survive. |
| Language model | Google Gemini free tier, `gemini-3.5-flash-lite` | Server-side key. Counterbill never falls back to another or paid model, and never to scripted output. |

Secrets, set only in the Render dashboard (never in git, never pasted into chat): `DATABASE_URL`, `GEMINI_API_KEY`. `PUBLIC_APP_URL` is not secret but is set by you. `SESSION_SECRET` is generated by Render. Leave `COUNTERBILL_INFERENCE` and `COUNTERBILL_ALLOW_TEST_IN_PRODUCTION` unset: the container refuses to start if `COUNTERBILL_INFERENCE` is present, and a production build refuses test mode.

## 2. Neon setup (about 5 minutes)

1. Create an account at neon.com (Free plan; no card).
2. **Create project**: name `counterbill`, a current Postgres version, and the region **AWS Europe (Frankfurt) / eu-central-1** so it is next to Render's Frankfurt region (`render.yaml` uses `frankfurt`; if you pick another Neon region, pick the Render region nearest it and edit `region:` in `render.yaml`).
3. Open the project and choose **Connect**. Choose your default branch, database (`neondb`) and role.
4. **Turn "Connection pooling" off** so the host does **not** contain `-pooler`. Counterbill uses session-level advisory locks for migrations, which a transaction pooler breaks.
5. Copy the connection string and make two edits to it, in a private place (not a chat, not a file in the repo):
   - change `sslmode=require` to `sslmode=verify-full` (same protection, and it silences the driver's warning about `require`);
   - delete `&channel_binding=require` if present.
   The result looks like `postgresql://USER:PASSWORD@ep-xxxx.eu-central-1.aws.neon.tech/neondb?sslmode=verify-full`. Neon's certificate is from a public authority, so no extra certificate setup is needed.
6. Keep it for step 3 below. You do not need to create tables: the container applies migrations on every start.

Things to know about Neon Free (check Neon's pricing page for today's numbers; they change): compute suspends after a few minutes without connections and wakes on the next one, storage is capped (about 0.5 GB), and compute hours are capped per month. The worker polls the database every 2 s while the Render instance is awake, which keeps Neon awake as well; when Render sleeps, so does Neon.

## 3. Render setup (about 10 minutes plus the first build)

1. Create an account at render.com, signing in with GitHub (Free plan; no card).
2. **New → Blueprint**, connect GitHub, grant access to `TheWeirdDee/counterbill` only, branch `main`. Render reads `render.yaml` and shows one service, `counterbill`, plan **Free**. If it shows any other plan or any extra service, stop.
3. When asked for the three values:
   - `DATABASE_URL`: the edited Neon string from section 2.
   - `GEMINI_API_KEY`: your Gemini key (the one in your local `.env`).
   - `PUBLIC_APP_URL`: `https://counterbill.onrender.com` for now (the service URL is only known after creation).
4. **Apply**. The first build takes several minutes (Docker). In **Logs** you should see, in order: `applied 001_init.sql` (and `002_…`), `[start] web on 0.0.0.0:10000, worker supervisor started`, `Ready in …`, `[supervisor] … ready (max 1 concurrent runs)`.
5. Open the service page and note the real URL. If it differs from the one you entered, change `PUBLIC_APP_URL` under **Environment** and let it redeploy. (It affects page metadata only; request checks use the Host header.)

## 4. Hosted verification: what has to pass before this is called deployed

Run these from your computer; they only call the public HTTP API and never print secrets. Replace the URL with yours. The first request after a sleep takes a while (section 5).

```bash
node scripts/hosted-check.mjs ready  https://YOUR-SERVICE.onrender.com   # database, worker heartbeat, model credential
node scripts/hosted-check.mjs run    https://YOUR-SERVICE.onrender.com   # investigation, survey revision, three exports (spends free-tier quota)
```

Then restart the service (Render dashboard → the service → **Manual Deploy → Deploy latest commit**, or **Restart service** if your plan shows it). Wait for the logs to show `ready`, then:

```bash
node scripts/hosted-check.mjs verify https://YOUR-SERVICE.onrender.com  # same case, letter and exports (byte-identical), SSE replay, 404/401 isolation
```

Finally the interruption test:

```bash
node scripts/hosted-check.mjs start https://YOUR-SERVICE.onrender.com   # returns once an agent is running
# restart the service now (same menu as above), wait until the logs show ready, then:
node scripts/hosted-check.mjs retry https://YOUR-SERVICE.onrender.com   # run is reported failed with a reason, then retry completes
```

Pass criteria: every line prints `PASS`. Also open the site in a browser, sign up, create a case, upload a `.txt` invoice, and confirm it is still there after the restart. If any line fails, send me the output (it contains no secrets) and do not announce the deployment.

## 5. Measured locally under the Render Free limits

The image was built with Docker (Node 22) and run with `--memory 512m --cpus 0.1`, against PostgreSQL 16 that **only accepts TLS** with a private CA, using `sslmode=verify-full`, on the real Gemini free tier. Render's own instance may burst or throttle differently; treat these as measurements of this container under those limits, not as a promise about Render.

| Question | Result |
|---|---|
| Does the image build and contain what `start` needs? | The original Dockerfile did **not**: `pnpm install` stopped on the unapproved `@embedded-postgres/linux-x64` build script, and `tsx` and `concurrently` were dev dependencies skipped by `NODE_ENV=production`. Fixed: build approvals for every platform, `tsx` is a runtime dependency, multi-stage build, no `concurrently`. Image 1.22 GB. |
| PORT and interface | `next start -H 0.0.0.0 -p $PORT` (verified with `PORT=10000`, served through the published port and through a reverse proxy). |
| Migrations before requests | They run first and the container exits non-zero (retrying 4 times, 5 s apart) if they cannot be applied; web and worker start only afterwards. Applying `001` and `002` on a new database worked. |
| TLS | Plain-text connection to the database: refused by the server (`no encryption`), container exits. `verify-full` with an untrusted CA: refused (`unable to verify the first certificate`). `verify-full` with the trusted CA: connects and migrates. **Not tested against Neon itself** (no Neon account here); its public certificate chain is the standard case. |
| Memory | Idle: 120 MiB. During a real investigation (web, supervisor and one run process): 188 to 229 MiB peak (cgroup memory, which includes file cache) of 512 MiB. No OOM kill. |
| Time | Cold start to answering requests: 145 s on a new database, 72 to 94 s on restart. Real first investigation: 175 s (11 model calls). Survey revision: 138 s (6 calls). |
| Concurrent runs | `MAX_CONCURRENT_RUNS=1` passes. With 3, **all three runs failed** with `worker_lost` after the 300 s startup lease and 0 model calls: at 0.1 CPU, three run processes cannot finish loading together. Memory was not the limit (no OOM). Failed runs were reported honestly and kept partial results; nothing was faked. `render.yaml` therefore sets 1. Each run still executes its six agents concurrently. Two concurrent runs were not measured. |
| Interrupted by SIGTERM mid-investigation (a deploy or a sleep) | The run is marked `worker_restarted` within seconds (4 s observed). After restart, **Retry** completed the investigation (assessment v2). |
| Interrupted by SIGKILL (crash) | The run stays `running` until its lease expires, then becomes `worker_lost` (116 s observed). **Retry** completed the investigation. |
| Cases, uploads, exports survive restart | After a graceful restart, the case, letter draft v3 and all three exports were present and **byte-identical** (SHA-256 compared). |
| Proxy, cookies, auth | Through an nginx reverse proxy with default buffering and `X-Forwarded-Proto: https`: session cookie `Secure; HttpOnly; SameSite=Lax`, sign-up, reload, sign-out, sign-in, cross-site POST refused (403), upload accepted, second account gets 404 for the case and its documents, signed-out gets 401. 15 of 15 checks. |
| SSE | First bytes in 1.1 s through the buffering proxy (`X-Accel-Buffering: no` works); reconnect with `Last-Event-ID` replays only what was missed. |
| Real model | `hosted-check run` against the container: 12 of 12 checks, on `gemini-3.5-flash-lite`, test mode off. |

What this does **not** show: Neon's behaviour (suspend and wake, pooled vs direct, connection limits), Render's proxy and its spin-down, the first deploy build on Render, or that Gemini's free quota is available to your key at that time.

### Limits you will notice on Render Free

- The service sleeps after about 15 minutes without requests and the next visit waits for a cold start (tens of seconds to a few minutes at this CPU share). A visitor who starts an investigation keeps it awake; one who leaves mid-run may find it interrupted if the instance is stopped, in which case the run is marked failed with a reason and can be retried.
- 512 MB RAM and 0.1 CPU: one investigation at a time (`MAX_CONCURRENT_RUNS=1`). A second one queues and starts when the first finishes.
- The model free tier is paced (`MODEL_REQUESTS_PER_MINUTE`, default 10) and has daily limits. A quota error ends a run with a clear message and partial results.
- `SESSION_SECRET` is generated for completeness; sessions use random tokens stored hashed in the database, so rotating it does not sign anyone out.

## 6. Health endpoints

- `/api/health` (used as Render's health check): 200 while the process and database answer; the body says whether the app is actually ready and lists reasons if not. A missing model key therefore does not make Render restart-loop the container.
- `/api/ready`: 503 unless the database, a worker heartbeat from the last 15 s and a model credential are all present. Use it in a monitor, and in `hosted-check ready`.
